# 1.x goal: 10× faster than 1.0

The first goal of the 1.x series is a graphviz-pure that is 10× faster than release 1.0.0, while every
output byte stays identical to C Graphviz 16.1.0 and the code stays safe Rust
(`#![forbid(unsafe_code)]`, no C dependencies, no C allocator). This page defines the number, records
the 1.0 baseline, ranks where the time goes, and budgets the gap. Work is tracked in the GitHub
milestone [1.x: 10× faster](https://github.com/graphviz-pure/graphviz-pure/milestone/9) (#607).

## Status

- **1.0.0 baseline (shipped Linux build): 0.54× C's speed** over the headline cases. Per engine:
  dot 1.18×, circo 1.77× (faster than C); neato 0.22×, fdp 0.38×, sfdp 0.54×, twopi 0.29×,
  osage 0.39×, patchwork 0.45× (slower than C). Peak RSS is 1.32× C's.
- **Speedup so far: 1.00×** (nothing has merged). The [budget](#budget) expects about 3.9–5.1×
  single-threaded from the work identified so far (4.3–5.8× with PGO), so **10× is not yet covered
  by a plan**. The `parallel` column and the [gap items](#closing-the-gap) are how it might be.
- **Much of the first gain is a build fix, not new algorithms.** The shipped Linux binary links
  musl's slow software `fma` ([below](#the-shipped-linux-binary-pays-for-musls-fma)). Building for
  x86-64-v3 (#531) removes that cost and is the largest item in the budget. The page counts it,
  because the metric is what users run, but reports it separately.
- The table in [Progress](#progress) is updated at every release.

## The metric

- **Speedup** = wall time of the shipped 1.0.0 release build ÷ wall time of the shipped build under
  test, same machine, same inputs, measured back to back by `scripts/bench/bench.py`.
- "Shipped build" means the binary a user downloads for the platform. For Linux x86-64 this is the
  static `x86_64-unknown-linux-musl` archive (at 1.0.0: x86-64-v1, musl's `malloc` and `fma`). The
  baseline uses that build of the 1.0.0 commit.
- **Headline:** the geometric mean of the per-case speedups over `scripts/bench/sets/full.tsv`
  (a case is one input and one `-T` format; its time is the median of 5 runs, or of the runs the set
  file gives), reported overall, per engine (dot, neato, fdp, sfdp, circo, twopi, osage, patchwork)
  and per output format (svg, plain, png).
- **Goal:** a geometric mean of at least 10×, and no engine below 3×.
- **Start-up cases are reported, not counted.** Cases that take 1.0 under 50 ms (11 of 72 in
  `full.tsv`: `unix.gv` in three formats, osage and patchwork `b51`, osage `b15`, patchwork
  `infosrc_plugins`, sfdp `attr_quadtree_none`, and the 1,000-node twopi, osage and patchwork
  graphs) are dominated by fixed costs: process start-up, static tables and output writing (a
  two-node graph takes about 4 ms), which no layout work can make 10× faster. They get their own row so a regression still shows. This is the one change from the
  owner's original definition.
- **×C** = C time ÷ port time, for every row, so above 1 means faster than C. C is 16.1.0 built
  on this machine with GCC `-O2` and without `-mfma` (`/opt/graphviz-16.1.0`, pango-free plugins, as in
  [baseline.md](baseline.md#method)), so it runs stock C's speed rather than the reference build's.
- **Peak RSS** is reported next to time as port ÷ 1.0. It must not regress (geometric mean ≤ 1.00,
  and no case above 1.10 without a reason in the release notes).
- **Single-threaded, default features** is the main number. A build with `--features parallel`
  (#609) gets its own column. It must produce identical bytes for any thread count.
- `scripts/bench/tenx.py BASE.json NEW.json` prints the table; `docs/perf/data/full-1.0.0.json` is
  the baseline.

### The shipped Linux binary pays for musl's `fma`

The 0.2.2 baseline measured the gnu build. The shipped musl build is up to 5.0× slower, and the
reason is the link, not the code: musl's `libc.a` defines a strong software `fma`, which replaces
compiler-builtins' weak `fma` that dispatches to the CPU's FMA instruction at run time. Every
`f64::mul_add` (389 sites) then costs about 145–170 instructions.

| input | musl ms | gnu ms | C ms | musl ÷ gnu |
| :-- | --: | --: | --: | --: |
| fdp viewport | 4,452 | 893 | 1,634 | 4.98 |
| fdp b69 | 532 | 119 | 300 | 4.48 |
| circo dotsplines_dot1 | 958 | 237 | 106 | 4.04 |
| twopi ngk10_4 | 824 | 221 | 105 | 3.72 |
| sfdp gen_rnd2000 | 839 | 389 | 662 | 2.16 |
| dot b29 | 1,318 | 953 | 1,615 | 1.38 |
| osage clustered_20000 | 571 | 449 | 223 | 1.27 |
| patchwork clustered_20000 | 554 | 446 | 274 | 1.24 |
| neato hw3_vpsc_random200 | 402 | 400 | 83 | 1.00 |

(median of 3, load 2.3–2.8.) neato is the same on both because its `f32` `fmaf` loop is bound by
call latency either way; only inline FMA helps it. osage's and patchwork's difference is musl's
`malloc`, not `fma`.

## Budget

Expected speedup over the 1.0 musl build, single-threaded, from the work identified so far. A

| :-- | --: | :-- | :-- | --: | :-- |
| neato | 11 | 4.5× (m: −78% instructions) | #533 kernel 2–3× | 9–15× | yes |
| fdp | 8 | 7× (m: 7.3× instructions) | flat positions 1.1–1.3× | 8–9× | yes |
| circo | 7 | 9× on the 2 `splines=true` cases (m: 4× musl→gnu, 2.8× +fma) | #597 2.9× instructions (m) on sparse | 4–4.5× | yes |
| twopi | 6 | 7–8× on the 3 spline/arrow cases | #598, #596, #610 on trees, 1.5–2× | 3.5–4× | yes |

The headline is the geometric mean of the engine ranges, weighted by each engine's case count.
PGO (#608) applies to every engine (typically 1.1–1.15×, not yet measured) and would make it about
4.3–5.8×.

**Is 10× reachable?** Not with the plan above alone. A 10× geometric mean needs 2–2.5× more than it
covers, and dot, osage and patchwork are at risk of missing the 3× floor. neato should pass 10× once
#531 and #533 land, and fdp should come close (8–9×). The rest of the gap has to come from the items below, and
each will be measured before it is counted.

### Closing the gap

- **The `parallel` column (#609)**: sfdp's repulsion, neato's mat-vec, fdp's overlap forces and the
  visibility graph are per-node work against frozen state, so they can run on every core with
  unchanged bytes. That is the realistic route past 10× for sfdp, neato and fdp, in the `parallel`
  column only.
- **dot**: after #594, the next steps are #537 and #538 (index newtypes, `NodeInfo` split by phase),
  then mincross and rank on the same layout. dot's network simplex must choose the same edges in the
  same order, so the gain is constant-factor, not algorithmic. A second profile after #594 decides
  how much more there is.
- **Allocation on musl**: on osage, patchwork and twopi, half the time is musl's `malloc`, `free`
  and the kernel calls behind them. A faster allocator would need `unsafe` (`GlobalAlloc`) or a C
  allocator, which are both ruled out, so the route is fewer allocations: #535, #536, #596, #610.
- **Start-up** is excluded from the headline but should not regress: the static tables and the
  layout thread spawn are about 4 ms.

## Reproducing

```sh
cargo build --release --locked --target x86_64-unknown-linux-musl -p graphviz-pure-cli
python3 -I scripts/bench/synth.py --out target/bench/synth
python3 -I scripts/bench/bench.py run --set scripts/bench/sets/full.tsv \
    --port target/x86_64-unknown-linux-musl/release/graphviz-pure --synth-dir target/bench/synth \
    --c-dot /opt/graphviz-16.1.0/bin/dot --c-gvbindir /opt/graphviz-16.1.0/lutplugins \
    --out target/bench/full.json            # about 75 minutes with C on a quiet machine
python3 -I scripts/bench/tenx.py docs/perf/data/full-1.0.0.json target/bench/full.json --cases
```

On a shared machine, hold every build slot and wait for idle CPUs before running. Compare only
runs from the same machine, and record `uptime` with the numbers. The profiles used
`perf record -F 1999 --call-graph fp` and `valgrind --tool=callgrind` on a frame-pointer build, as in
[baseline.md](baseline.md#profiles).
