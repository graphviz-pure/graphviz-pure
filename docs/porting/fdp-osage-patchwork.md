# fdp, osage and patchwork ports (Graphviz 16.1.0)

`layout=fdp`, `layout=osage` and `layout=patchwork` now run function-by-function
ports of `lib/fdpgen`, `lib/osage` and `lib/patchwork`. They are built on the
shared neato-family infrastructure (`common`, `pack`, `neatogen` overlap removal
and edge routing, `pathplan`, `ortho`; see `docs/porting/neato.md`). The old
approximations in `force_circular.rs` are gone.

Entry points:

- `graphviz_pure_layout::fdpgen::layout::fdp_layout(&mut Graph)`
- `graphviz_pure_layout::osage::osage_layout(&mut Graph)`
- `graphviz_pure_layout::patchwork::patchwork_layout(&mut Graph)`

## Fidelity

`gv-diff` against C 16.1.0 goldens (built-in text metrics, `scripts/gen-golden.sh`):

| corpus | before (force_circular) | after |
|---|---|---|
| `tests/fdp` (383 files; 377 at the start) | 68 exact, score 102.6/377 (27%) | 383 exact (100%) |
| `tests/osage` (178 files; 176 at the start) | 1 exact, score 20.9/176 (12%) | 178 exact (100%) |
| `tests/patchwork` (140 files) | 14 bb ok, score 20.4/140 (15%) | 140 exact (100%) |
| main corpus (508 files) | 250 exact at branch start | 504 exact with the other merged ports; every fdp/osage/patchwork file exact, never a regression |

Layouts are bit-identical to C wherever checked: floating-point expressions
follow clang's `-ffp-contract=on` code generation (`a*b + c` is
`fma(a, b, c)`; for `a*b + c*d` the first product is fused), checked against
the disassembly of the C objects. Random numbers (`drand48` reseeded per
component, libc `rand()` for coincident points), the Apple `qsort`, cgraph
node/edge orders and cdt grid order are reproduced.

### Derived graphs

Each graph (root or cluster) is laid out through a derived graph `DG` with one
node per own node, child cluster and inherited boundary port. Shared code that
works on an `LGraph` (packing, `removeOverlapAs`, `compute_bb`) runs on an
`LGraph` built from the derived nodes by `layout::with_lgraph`, which copies the
positions back. A derived graph is a root of its own (`agopen`), so it has the
command-line graph attributes (`Graph::protograph_attrs`); `copyAttr` then copies
`overlap`, `sep` and `K` from the input graph. So in-file `normalize`, `scale` and
`esep` have no effect inside fdp's overlap removal, while `-Gnormalize`, `-Gscale` and
`-Gesep` do, and the root level runs `normalize(cg)` before `fdp_xLayout`, as in C
(#398).

cgraph orients derived edges (`hd > tl`), orders multi-edge ports
(`n < other`) and port edges (`dn > m`) by `Agnode_t` address. `NodeHeap`
models macOS's allocator for that size class: slots of a freed derived graph are
handed back LIFO to the next one, then fresh increasing addresses. With
cluster edges, `processClusterEdges` frees memory of other zones that C's
derived nodes later reuse; creation order matches C on those inputs, so the
model does not recycle there.

### Cluster edges

`processClusterEdges` mutates the graph in C. The port builds the modified graph
(`ClusterEdges::work`: cluster-named nodes deleted, one `__0:<cluster>` node per
cluster — C's name counter never advances — and cloned edges) and maps the
layout back. The deleted nodes keep default attributes and carry
`NodeLayout::clust_node`, which tells the renderers neither to draw them nor to
print layout attributes; edges of deleted nodes that were not re-attached are
removed, as in C.

The work graph is that same cgraph, so it also keeps its attribute dictionaries:
`deriveGraph`'s `agopen("derived")` inherits cgraph's ProtoGraph — the
command-line `-G` declarations — as its defaults, and the port reads them
through `Graph::protograph_attrs`. Issue #431 found the port dropping them (the
work graph had no dictionaries, so `-Gnormalize` never reached the derived graph
and `normalize(cg)` did nothing); the fix carries the dictionaries over. C's
derived-node addresses stay in creation order on those inputs (`GVDBG3` on an
instrumented C: `nonmono=0`), so the `NodeHeap` model above is unaffected.

## Gaps and differences

- `start=regular`, `start=self` and `start=random` without a number seed C's
  generator from the clock; the port uses seed 1.
- C's address-dependent orders are not reproducible run to run on some inputs
  (e.g. many nested clusters with `splines=compound`): two C runs can differ,
  and the port matches one of them or neither. No corpus file is affected.
  An overlap mode with no try count (`overlap=compress`) runs `removeOverlapAs`,
  and so `normalize`, on every cluster's derived graph (`fdp_xLayout`). With
  `normalize`, that rotates the cluster by the angle of its first derived edge,
  whose direction is the `hd > tl` address order: the cluster comes out turned
  by 180 degrees on some runs (#476, the same cause as #34).
- `splines=compound` in osage keeps that edge type. C's `spline_edges_`
  does the same: a multi-edge is a cubic (`edgetype == EDGETYPE_PLINE`
  is false), and a single edge still falls through to `makePolyline`.
- With cluster edges and `splines=true`, C warns and draws lines; the port does
  the same. A partial `compoundEdges` failure keeps the routed edges as C's
  `Nop = 2` does, but their boxes may grow the graph box slightly differently.
