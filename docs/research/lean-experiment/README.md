# Experiment: improvement through math proofs

Milestone: [Improvement through Math Proofs](https://github.com/graphviz-pure/graphviz-pure/milestone/10).
Started 2026-11-03. Survey that motivated it: [`../lean-bend-survey.md`](../lean-bend-survey.md).

## The bet

graphviz-pure must reproduce C Graphviz 16.1.0 byte for byte. That turns every speedup into an
equation: the fast path must return the same integers, or the same IEEE doubles through the same
rounding sequence, as the mirror of C's code. The repo already writes such arguments in prose
(`docs/perf/ns-cut-sets.md`, `mincross-scans.md`, `circo-crossings.md`, `spline-cubic-634.md`) and
checks them at runtime with `*-check` Cargo features. The bet is that writing them in Lean 4 instead:

1. finds gaps the prose missed (a finding even when the code is right),
2. lets us ship speedups whose equivalence argument is too fiddly to trust in prose
   (incremental circo deltas, the network-simplex leave-edge index, float reuse in spline routing),
3. is cheap enough to be a merge gate, with the proof stated over the shipped Rust via
   Rust-to-Lean extraction (Aeneas), not over a hand-written model.

The experiment is scoped to measure all three. It ends with a write-up of what the proofs bought
in wall time and in bugs, and what they cost in hours.

## Working on it

Lean lives outside the Rust toolchain. On the shared machine it is installed under
`/jobs/work/gvp-lean/` (elan, Lean 4.35.0, the Aeneas checkout); `scripts/proofs/lake.sh` finds it
through `GVP_LEAN_HOME`. Elsewhere, install [elan](https://github.com/leanprover/elan), and the
`lean-toolchain` file selects the version.

```sh
scripts/proofs/lake.sh exe cache get   # once: Mathlib's prebuilt oleans
scripts/proofs/lake.sh build           # every GvpProofs/**.lean must compile, no sorry
```

CI's `proofs` job (`.github/workflows/ci.yml`) runs `lake exe cache get` and `lake build` in
`proofs/` when a change touches `proofs/` or `scripts/proofs/`.

### Installing Charon and Aeneas (extraction only)

Proofs build without them; only re-extracting Rust needs them. On the shared machine they are
already built under `/jobs/work/gvp-lean/`, and `env.sh` there sets the paths. To set them up
elsewhere, under one directory `$GVP_LEAN_HOME` (wall-clock times from the first install, on 4 jobs
at `nice 15`):

1. opam 2.6.1 (the static release binary) and an OCaml 5.3.0 switch:
   `opam init --bare --disable-sandboxing`, `opam switch create aeneas ocaml-base-compiler.5.3.0`
   (3 min). zarith needs GMP headers; without root, build GMP 6.3.0 statically into
   `$GVP_LEAN_HOME/gmp` (35 s) and point `C_INCLUDE_PATH`, `LIBRARY_PATH` and `PKG_CONFIG_PATH`
   at it.
2. `git clone https://github.com/AeneasVerif/aeneas $GVP_LEAN_HOME/aeneas`, check out the commit
   pinned as `aeneas` in `proofs/lakefile.toml`, then `opam install ./src --deps-only` (80 s).
   Keep `opam env`'s `CAML_LD_LIBRARY_PATH` set, or dune fails with `dllzarith.so: No such file`.
3. Charon at the commit in `aeneas/charon-pin`, cloned into `aeneas/charon`. Its nightly
   (`nightly-2026-09-17` for this pin) needs only `rustc-dev`, `llvm-tools`, `rust-src` and
   `rustfmt`: `rustup toolchain install nightly-2026-09-17 --profile minimal --component rustc-dev
   --component llvm-tools --component rust-src --component rustfmt` (1.6 GB). Build with
   `RUSTUP_TOOLCHAIN=nightly-2026-09-17 make build-charon-rust` and `dune build` in
   `aeneas/charon` (4 min). `make setup-charon` does the same but runs Charon's whole test suite,
   which needs every target listed in Charon's `rust-toolchain`.
4. `make build-dev` in `aeneas` (2 min) gives `aeneas/bin/aeneas`. `aeneas -version` must print
   the pinned commit; `scripts/proofs/extract.sh` refuses to run otherwise.

Set `CHARON_CACHE_DIR` to a directory on a large disk: by default Charon writes under `~/.cache`.

### Re-extracting

```sh
scripts/proofs/extract.sh crates/graphviz-pure-layout CircoCount \
  --start-from crate::circogen::blockpath::count_indexed \
  --start-from crate::circogen::blockpath::count_all_crossings_reference
  # one module directory per extraction; its extract.args records the exact filters
scripts/proofs/extract.sh --check                          # before a PR: committed files are current
```

The first form writes `proofs/GvpProofs/Extracted/<Name>/{Types,Funs}.lean` and an
`extract.args` file that records the command. `FunsExternal.lean` beside them is hand-written:
Aeneas lists the standard-library functions it has no model for, the script seeds the file from
that list, and each `axiom` in it should become a definition. `#print axioms <theorem>` shows
which ones a proof still rests on. `--check` replays every `extract.args` and diffs. CI builds the
committed files but does not extract, so run `--check` yourself when a PR touches extracted Rust.
What extraction accepts in this codebase, and what it rejects: [`extraction.md`](extraction.md).

Adding a proof: create `proofs/GvpProofs/<Engine>/<Name>.lean`, state the theorem in the
"fast path = C-mirror path" shape, keep the matching `*-check` feature until the file is sorry-free,
then say in the PR which runtime check the proof retires. Branch names follow the perf scheme:
`proofs/<issue>-<slug>` for Lean-only changes, `perf/<issue>-<slug>` when Rust changes too.

Float lemmas use [FloatLib](https://github.com/lean-dojo/FloatLib) (`lean-dojo/FloatLib`, pinned by
commit in `proofs/lakefile.toml`), a Flocq-style bit-exact model of IEEE binary formats. It targets
the same Lean and Mathlib versions as this project, so it adds no second Mathlib. Import
`FloatLib.Floats.Formats.BinaryInterchange.Semantics` and work with `Model binary64`; the first
user is `GvpProofs/Geom/LimitBoxes.lean` (#733). Its friction is logged in the journal.

Lean version policy: pinned to the toolchain Aeneas's Lean backend requires (`v4.35.0` on
2026-11-03) and to the Mathlib tag of the same name. Bump both together, in their own PR.
