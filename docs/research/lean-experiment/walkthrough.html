Faster algorithms, with the proof that nothing changed

graphviz-pure has to produce the same bytes as C Graphviz. That makes every speedup an equation, and equations are what a theorem prover checks. This page follows one speedup through the whole process, then steps back to show the nine tickets, what the reviews found, how far the proofs reach, and what is still missing.

01 · the claim

A speedup, stated as an equation

Ticket #730 asks circo to stop recounting every crossing after each tentative node move, and to update the count from the moved node's edges alone.

Why it works this way

graphviz-pure has to match C Graphviz 16.1.0 byte for byte. So a faster path may not be "close": it has to make the same keep-or-reject decision on every move, including the wrapping i32 total it compares. A speedup becomes an equality between two computations. That is what a Lean theorem is for.

circo was worth the effort. The recount was about 80% of its instructions on a 200-node graph, and its running time grew as n3.1.

a claim with no evidence yet
02 · check the claim

Check the ticket's idea against C before writing any Rust

The delegate derived a formula and ported C's own loop to Python. Over 29,004 tentative moves the formula matched C exactly. The ticket's premise did not hold: a moved node's own edges are not enough.

Why it works this way

Moving one node shifts the position of every node between its old and new place, so the change depends on prefix sums over the whole list plus the moved node's sorted neighbour ranks. A ticket is a plan, not a fact. The cheap test of a plan is a second implementation of the thing it must equal, written before the fast code exists.

premise replaced: prefix sums over the list
03 · state it in Lean

Lean makes you state what the code must check

Three theorems say that the pair count is a closed formula, that moving a node changes it by a constant plus phi(cut), and that old total plus the wrapped delta equals the wrapped recount.

They only go through under three conditions: no loops, symmetric adjacency, distinct positions.

Why it works this way

The kernel will not let you assume what the code does not check. Each condition the proof needed became a line in the code's eligibility test, instead of an unwritten assumption about "normal" graphs.

Predict: a block contains a self-loop. What does the shipped code do?

It runs the full recount. Delta::new returns None for loops, parallel edges, repeated list entries, or a list that is not a permutation of the block, and the old loop runs. On the corpus the delta applied to all 37 non-trivial blocks in 282 circo inputs. The reviewer later found that no test actually built a parallel edge, because CGraph::edge merges them, so one was added.

04 · ship it

The Rust, with the old counter kept as its judge

A tentative move now costs O(degree). The list is touched only when a move is kept. count_all_crossings stays: under the circo-check feature it recounts every move and asserts the same integer, and lists of 16 or fewer still use it.

Why it works this way

A proof about a model is not a proof about the code. The kept counter is the bridge: if the Rust ever drifts from what Lean proved, the check fails on the first move where they differ. The arithmetic is the other bridge. In release the total wraps at 232 and the accept test reads the wrapped value, so the delta is added with the same wrapping, and debug builds panic exactly where the recount would.

05 · measure

Measure on the same inputs, against 1.0 and against C

On circo_sparse_400 the run takes 5,466 ms in v1.0.0, 184 ms before this change, and 29 ms after. C Graphviz takes 54,057 ms. The exponent drops from about 3.1 to about 1.9.

Why it works this way

The comparison that counts is against 1.0, because the milestone is "10× faster than 1.0"; the gain over yesterday's master alone would hide the work before it. The exponent stops at 1.9 because one quadratic piece is left: each node still builds its prefix sums in O(n+m). Two circo inputs did not move, because their time is spline routing. The report says so.

06 · review

A model from another family tries to break it

GPT-6.1 Sol read the Rust and the Lean side by side and ran 3,000 random seeds, 1,179,648 exhaustive cuts, 624 cuts across the signed i32 boundary and seven adversarial DOT inputs against C's bytes. It found one gap: no parallel-edge test.

Why it works this way

Lean's kernel checks the proof. It cannot check that the model is the code, or that the hypotheses hold where the code is called. A reviewer from the author's own family tends to agree with the author, so this one comes from another. Its brief is the diff and the rules, not the author's conclusion. Across 15 reviews it raised no false alarm and found something in 14.

07 · gate

CI is the last gate, and it is everyone's gate

36 checks passed, including byte-identical output across platforms, the circo check mode, the perf ratchet and the Lean build. It merged as fa500e4a.

Why it works this way

The proofs add checks. They do not replace the project's own. The Lean job builds against Mathlib in 7 to 15 minutes (about 9,000 build jobs); the byte-equality jobs are what say the output did not move. More than once, CI jobs were cancelled by something outside the project; they were re-run, never skipped.

08 · the other eight

The same pipeline ran nine times

Four tickets shipped a speedup. Two formalised arguments the code already relied on. One built the tooling. Two ended without a speedup, and that was the right outcome.

Why it works this way

The stress-mat-vec gate was measured first: it fires on 1.6% of calls, so no code was written. The canreach cache has nothing to speed up, and writing its Lean statement showed the obvious design, memoising answers, would have been wrong, because edges are appended between queries. Two of the four speedups began with a ticket premise that turned out wrong. A pipeline that can only say yes is a rubber stamp.

09 · what the reviews found

What 15 reviews found

The worst: the network simplex theorem assumed the tree's numbering was current, which is true at the first pivot and false after it (P1, reproduced through rank2). Another P1: making a BFS extractable had added 8 to 15 allocations to shipped twopi code.

Why it works this way

Proofs fail in one way: they are true, about something slightly different from what runs. Every finding is of that kind: model against code, hypothesis against call site, claim against scope. All were fixed on the PR before merge. The first became a follow-up proof (#750) and a stronger runtime check (#765): the old check renumbered after every pivot, so it could never have seen a search that read stale numbers.

10 · how far down

How far down does the trust go?

Three levels: a prose argument; a Lean theorem over a hand-written model; a Lean theorem over the Lean that Aeneas generates from the shipped Rust. Of the nine tickets' main theorems, how many are at the third level, over the extracted Rust?

Why it works this way

Extraction only accepts code of a certain shape: one early-exit loop per function, no closures, no floats. Making circo's counters extractable took a refactor that cut Aeneas's time from 850 seconds to 10. Making twopi's BFS extractable first cost 8 to 15 allocations (rejected), then needed a zero-copy rewrite, and one accessor is still modelled by hand.

One end-to-end theorem (2,608 lines, #770), plus the Fenwick lemmas. Everything else is over a model with a written list of differences. And it is silent above i32::MAX, because Charon compiles with debug assertions: the checked reference fails where release wraps, and a complete 403-node block already has about 2.17 billion crossings. The model proof keeps that regime. It is also 64-bit only, so wasm32 is outside it.

11 · not there

What is only argued, and what is not built

Prose only: the zero-guard and no-NaN argument for the spline retry; the network simplex tie-climb budget and the assumption that the fallback's renumbering is valid; mincross reordering; the graph facts callers guarantee, audited by reading but not proved.

Not built: floats cannot be extracted yet (Aeneas support is a draft upstream); wasm32; the overflow regime over extracted code; no theorem yet depends on the twopi extraction.

Why it works this way

The honest map matters more than the list of wins. A reader who sees "proved" should know which part of the claim is covered. Each gap has a named home in a file header or an issue, so none hides inside a hypothesis.

12 · next

Where we go next

Next speedups: the network simplex cut-set moves (about 11% of instructions on the 20,000-node DAG), and circo's per-node prefix build. Make the packing code deterministic so the ratchet's instruction gate is trustworthy. Decide whether to report the Aeneas and Charon bugs we found. Then write the account of how it went. PR #775, the twopi extraction, has merged.

Why it works this way

The nine tickets taught a pattern: measure before proving (the stress gate), derive before coding (circo), and expect the ticket to be wrong (two of four). The next targets come from profiles, not hope. The 11% is the ceiling for what is left in network simplex.

What the code does not tell you
CHECK is a compile-time constant, true in tests and under the circo-check feature. In a release build the recount branch is only reached when the delta declines, so the oracle costs nothing where it does not run, and the proof is what stands in for it there.

Decisions that are not ours to make

  1. Report the Aeneas and Charon bugs we hit (two in Aeneas, one panic in Charon) to the upstream projects, or keep them in our notes.
  2. Whether the end-to-end theorem should become a merge requirement for future circo changes, or stay a one-off.
  3. Whether to pursue floats: wait for Aeneas's float support, or model float code by hand as we did for the spline retry.
