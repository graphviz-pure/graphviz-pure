# graphviz-pure 1.0

1.0 is "the current port without known bugs", with a public API stable enough that the work
after it (speed, memory, idiomatic Rust) can happen behind it without breaking anyone. This
document says what that means in checkable terms, what stands between master and it, and what
only the maintainer can decide. Progress is tracked in the
[`1.0` milestone](https://github.com/graphviz-pure/graphviz-pure/milestone/7).

Every number below was measured on master at `f9c2fd1d` (0.2.2) on 2026-10-27. The command
that produced it is given next to it or under [How this was measured](#how-this-was-measured).

## Definition of done

1.0 ships when every box below can be ticked. Each one is a command or a query, not a judgement.

### Fidelity

- [ ] **F1. Every stable corpus input is byte-identical to C.** `gv-diff e2e` reports
  `identical == files` for every corpus, and the layout (`gv-diff`, eight baselines) and render
  (`gv-diff render`, seven formats) ratchets report no inexact file outside the accepted list in
  F2. *Today: met* (see [Where fidelity stands](#where-fidelity-stands)).
- [ ] **F2. Every input that is skipped or inexact has a recorded cause in an accepted class**:
  C nondeterminism or undefined behaviour, a C crash or assertion, C's error path, or the
  platform libm (docs/versioning.md). The cause is on the What's left page or in
  `docs/porting/`. *Today: 12 of the 14 skipped inputs have one* (#502).
- [ ] **F3. No open fidelity bug in the port.** No open issue labelled `fidelity` or `bug` lacks
  `wontfix`. *Today: 7 open, all in progress* (#475, #476, #488, #489, #490, #494, #496).
- [ ] **F4. A differential fuzz round on the 1.0 candidate**, of at least 6,000 new seeds over
  all eight engines, has every differing case fixed or triaged into an F2 class (#511).
- [ ] **F5. What's left is true.** Every `tests/fuzz-open/` entry and manifest flag matches
  its GitHub issue, and every open fidelity issue or accepted difference is listed (#502).

### Robustness

- [ ] **R1. No open `crash` issue.** *Today: met* (7 `crash` issues, all closed).
- [ ] **R2. The pre-release ClusterFuzzLite run passes on the 1.0 release branch**, as
  docs/releasing.md already requires for every release.
- [ ] **R3. The panic-site ratchet runs in CI and no count is above `tests/panic-sites.tsv`.**
  *Today: met* (9,985 sites against a baseline of 9,988). Whether 1.0 also needs a target count
  is [open decision D5](#d5-panic-sites).

### Rust and JS API

- [ ] **A1. The stable surface is declared**: docs/versioning.md and the crates' docs say which
  crates, modules and items semver covers ([D1](#d1-stable-rust-api-surface)), and the
  decisions in D2–D4 are implemented.
- [ ] **A2. CI checks the API.** `cargo semver-checks` runs against the last release for the
  stable crates (#507).
- [ ] **A3. The declared minimum Rust version is true and tested in CI** (#504).
- [ ] **A4. Nothing deprecated or promised for removal is left** in the published crates (#506).
- [ ] **A5. The wasm package reports itself correctly**: its `version()` and
  `supportedFormats()` (#505).

### Docs are true

- [ ] **D-2. Every number in README.md, the site and docs/ comes from the current ratchets**,
  and nothing describes something already fixed or shipped as pending (#508).
- [ ] **D-3. docs/versioning.md covers every channel and states its exceptions** (#509).

### Security and licensing

- [ ] **S1. SECURITY.md matches the workflows**, and the READMEs say that SVG from untrusted
  DOT is untrusted markup (#510).
- [ ] **S2. The supply-chain job passes**: `cargo deny`, `THIRD-PARTY-LICENSES.md` up to date,
  and the crate notices in place. These are existing CI checks; they must be green on the
  release commit.
- [ ] **S3. The supported-versions policy for 1.x is written down** ([D9](#d9-security-support-after-10)).

### Release

- [ ] **P1. 0.2.2 is out.** Release PR #501 was merged on 2026-10-26, but there is no `v0.2.2`
  tag and no channel has 0.2.2 (`gh release view v0.2.2`: release not found; crates.io, npm,
  JSR, PyPI and Wasmer all report 0.2.1). The maintainer tags the merge commit (docs/releasing.md).
- [ ] **P2. 1.0.0 is published on every channel docs/channels.md marks ready**, and
  `scripts/release-verify.sh` passes for each.

**Accepted differences outside the corpora.** Closed as not planned, with the reason recorded:

- #32 to #43 are fuzz-open entries `023`–`034`: C undefined behaviour,
  crashes, and clock- or address-dependent output. #40 is platform libm only.
- #28, #141: neato and circo multispline ends 0.1pt off. These are GTS face-order ties, like #35.
- #154: fdp ortho around overlapping `fixedsize=shape` nodes.
- #101: `pack` with a node in two non-nested clusters. C prints `node … belongs to two
  non-nested clusters` and lays out on shared records (docs/porting/crashes.md). This is C's
  error path; it has no `wontfix` label and no What's left entry (#502).

None of these is a 1.0 blocker under the classes in F2.

**A cross-check, and its limits.** The whole corpus was also run through C 16.1.0 built on
Linux x86-64, with the port's math and Apple's `qsort`/`rand` interposed (the
`scripts/c-oracle-linux` set-up, run without Docker). Built with `CFLAGS=-O2` that build
reproduced the committed references on only 2,093 of 2,595 stable inputs. x86-64 clang fuses
no multiply-adds unless it is given `-mfma`, while the arm64 build fuses them. With `-mfma`,
which the Dockerfile now adds on x86-64 (#519), it reproduces 2,588. That is every input of
neato, twopi, patchwork and the render corpus (docs/porting/libm.md, "Linux x86-64"). The 7
left are 3 fdp layouts that depend on heap addresses, 2 NaN cases (a printed NaN sign, a
NaN converted to `int`), 1 GTS run-to-run order and 1 timeout. The reference stays C as built
on macOS arm64, but a new corpus input can now get its references on Linux. The exceptions,
which still need the maintainer's macOS set-up, are fdp inputs, inputs involving a NaN, and
the stock-C files (`e2e.json`, `structure.json`).

## Feature coverage against C 16.1.0

- **Engines:** all of C's: `circo dot fdp neato nop nop1 nop2 osage patchwork sfdp twopi`
  (`graphviz-pure -Kfoo` lists the same set as C's `dot -Kfoo`).
- **Output formats.** The port has 17 names: `canon dot dot_json gv json json0 plain
  plain-ext svg xdot xdot1.2 xdot1.4 xdot_json`, plus raster `png jpg jpeg jpe`. Of the formats
  in C's core plugin, the port lacks 15: `cmap cmapx cmapx_np eps fig imap imap_np ismap pic
  pov ps ps2 svg_inline svgz tk`. C's `vt` and `kitty` terminal plugins, and the cairo/gd
  formats (`pdf`, `gif`, ...), are not ported either. The source is the list C's `dot -Tfoo`
  prints with the full plugin directory. Which of these 1.0 promises is
  [open decision D6](#d6-output-format-scope).
- **Command line:** `graphviz-pure -?` prints C's usage text word for word, apart from the
  program name. `-x -y -s -q -O -l -c -P -G/-N/-E/-A`, the `-L` fdp options and the
  `-T fmt:renderer` forms all exit as C does on a test graph; `-c` succeeds where C fails
  because it has no plugin directory to write. 299 tests in `crates/graphviz-pure-cli/tests/cli.rs`
  cover the rest.
- **Attributes** are not measured separately. The evidence is the corpora above, plus C's own
  test graphs (379/379 per dot variant, README).
- **The C bug ledger** (`docs/c-bugs-ledger.md`) named code that no longer exists: `dot.rs`,
  `network_simplex_solve`, `NS_MAX_ITER`, `geom/src/splines.rs`. It also said `compound.c` and
  `pathplan` are not ported; both are (`dotgen/compound.rs` has `make_compound_edge`, and
  `geom/src/pathplan/` has all of `lib/pathplan`). This pull request corrects rows 001–010
  and 014.

## Non-goals

1.0 does not promise:

- **That every old `#NNN` reference resolves.** Issues and pull requests #165–#457 were
  opened by an agent account GitHub has since suspended, so about 736 references to them
  return 404. They stay as a historical record (#503, closed as not planned).
- **Identity with stock C on a platform's libm.** Every build uses the same math library, and
  differences from Apple's or glibc's libm are not bugs (docs/versioning.md, #40).
- **Identity with C built with Pango**, or with a C build other than the reference. Text is
  measured with C's built-in metric tables, as the reference build does.
- **Reproducing C's nondeterminism, undefined behaviour or crashes.** Where C's output depends
  on addresses, the clock, freed or uninitialised memory, the port gives one stable answer.
  Where C crashes or asserts, the port draws something sensible.
- **Pixel identity of raster output** (`-Tpng`, `-Tjpg`). C draws with cairo and Pango; the
  port rasterises its own SVG with resvg. Only the layout is C's.
- **Graphviz's other programs**: `gvpr`, `unflatten`, `tred`, `ccomps`, `sccmap`, `gvpack`,
  `acyclic`, `nop` as a program, converters and others. C 16.1.0 installs 36 programs in `bin/`;
  the port is `dot` and its library.
- **A newer Graphviz.** The reference stays 16.1.0. Moving to a newer release is a major
  version (docs/versioning.md).
- **Speed and memory.** These are the post-1.0 work. 1.0 only has to leave room for it (D1).

## Open decisions

These are scope calls for the maintainer. No issue is filed for them until they are made.

### D1. Stable Rust API surface

There are about 1,120 public items across the seven library crates. layout alone has 716,
with 113 modules (one per C file), 87 structs whose fields are all public, and C-shaped types
such as the `Agraphinfo_t` mirrors in `dotgen/types.rs`. The facade `graphviz-pure` re-exports
`Graph`, whose 128 public fields reach 33 core types. It also re-exports the C-emulation
helpers `RandState`, `with_rand_state`, `FdpParms`, `set_y_invert`, `loadimage_installed`,
`plugins` and `decoded::*`, which only the CLI uses. Freezing all of that would freeze the
port's internals: no refactor after 1.0 could change a struct field.

- (a) Everything published is stable, as docs/versioning.md says today. Simple, but it blocks
  most post-1.0 refactors.
- (b) **Recommended.** Only the facade `graphviz-pure` (render, parse and layout entry points,
  options, the error type) and `graphviz-pure-raster` are stable. core, parser, geom, layout
  and render stay published, because the facade depends on them, but versioning.md and each
  crate's top-level docs declare them implementation crates with no semver promise. The facade
  pins them with `=` requirements. The CLI-only helpers move behind `#[doc(hidden)]` or a
  CLI-only path. `Graph` becomes opaque, with accessors, or leaves the facade.
- (c) Like (b), but rename the implementation crates `graphviz-pure-*-internal`. This is
  clearer for users, but it means new crate names on crates.io.

### D2. `#[non_exhaustive]` and the error type

No public type has `#[non_exhaustive]` (0 across all crates). Without it, adding an engine,
a format, an option field or an error variant breaks semver. The types involved are
`LayoutEngine`, `OutputFormat`, `RasterFormat`, `LayoutOptions` (all public fields) and
`GraphvizError`. `GraphvizError` exposes cgraph's `line: i32` and a `stage: &'static str`.
raster returns `Result<_, String>`, and 25 public functions in geom, layout and raster do too.

- **Recommended:** before 1.0, mark the stable enums and option structs `#[non_exhaustive]`,
  give options a constructor or builder, make the error an opaque struct with a
  `#[non_exhaustive]` kind enum, and give raster the same error type.
- Alternative: leave them as they are, and accept a major bump whenever an engine or format is
  added.

### D3. serde in the public API

core derives `Serialize`/`Deserialize` on 36 public types, `Graph` among them. That makes
serde 1.x a public dependency, and arguably makes `Graph`'s serialised form a contract
alongside `-Tjson`.

- **Recommended:** drop serde from the stable surface (keep it on internal types if wanted).
  The JSON contract is `-Tjson`/`-Tjson0`, which C defines.
- Alternative: keep it, and treat the serialised form as stable.

### D4. MSRV policy

The declared 1.85 is false (#504 makes it true). The open question is the policy after that.

- **Recommended:** declare the version CI tests, and allow raising it to any stable release
  that is at least six months old, in a minor version (as versioning.md already says).
- Alternatives: "latest stable only", which is honest but makes every bump a minor; or a fixed
  long-lived MSRV, which forbids let-chains and other features the code already uses.

### D5. Panic sites

The ratchet counts 9,985 sites in layout and geom: 256 `unwrap`, 42 `expect`, 7,568 indexing and
2,119 integer arithmetic (`scripts/panic-sites.sh`, clippy 0.1.99). Most indexing and arithmetic
sites are faithful C, correct for every input C accepts. docs/porting/crashes.md deliberately
fixes crashes at their cause, not site by site.

- **Recommended:** no target count for 1.0. Gate on R1 (no open crash), R2 (a clean fuzz run)
  and the ratchet (R3). Optionally, aim for 0 `unwrap`/`expect` (298 sites) as post-1.0 work,
  since those are the cheapest to make explicit.
- Alternatives: require 0 `unwrap`/`expect` before 1.0, or a fixed reduction in total. That is
  real work, with no fidelity gain and a risk of regressions.

### D6. Output format scope

The port lacks 15 of C's core formats (above). Python tools ask for some of them by default
(docs/python.md): `ps` (pydot, Keras), `cmapx` (Sphinx HTML), `svg_inline`, and `pdf`
(`graphviz`'s default, cairo in C).

- **Recommended:** 1.0 promises the formats it has. versioning.md already makes adding a
  format a minor version, so `svg_inline`, `cmapx` and `ps` can follow in 1.x. List the missing
  formats explicitly in README and versioning.md, so the CLI contract is unambiguous.
- Alternative: port `svg_inline` and `cmapx` before 1.0 (they are small and need no layout
  work) to unblock Sphinx and the Python wrappers on day one.

### D7. Fuzzing cadence

Coverage-guided fuzzing runs only when dispatched before a release (`fuzz.yml`, about an hour,
no schedule). Its corpus is a workflow artifact kept for 90 days, so a gap of more than 90 days
between releases loses it.

- **Recommended:** add a weekly scheduled run, which keeps the corpus alive and finds crashes
  between releases, and keep the pre-release gate.
- Alternatives: apply to OSS-Fuzz, or keep per-release only.

### D8. Untrusted input: limits and time

SECURITY.md invites reports of hangs on crafted input, and docs/porting/crashes.md says the port
must not panic, hang or run out of memory. There is no documented input-size or time limit and
no cancellation API. The fuzz targets skip graphs over 50 nodes, 100 edges or 8 KiB, so
superlinear cost is never exercised, and web/README.md's Worker example renders a request
body as it comes.

- **Recommended:** for 1.0, document that layout cost is superlinear and unbounded, as in C, and
  that services should run it under their own time and memory limits (a worker with a timeout).
  Add a limits or cancellation API post-1.0 as an additive minor.
- Alternative: add a limits API before 1.0.

### D9. Security support after 1.0

SECURITY.md says "only the latest release receives fixes".

- **Recommended:** keep that for 1.x: the latest minor gets fixes. 0.x gets none after 1.0.0.
  Say so explicitly.
- Alternative: support the previous minor for a fixed period.

### D10. Shape of the JS API

The npm API throws plain strings, not `Error` objects. `supportedEngines`, `supportedFormats`
and `inspectGraph` return JSON strings rather than arrays and objects, and the only TypeScript
types are what wasm-bindgen generates. Each of these is breaking to change after 1.0.

- **Recommended:** before 1.0, throw `Error` (with the message and C's exit status), return real
  arrays and objects, and ship a hand-checked `.d.ts`.
- Alternative: freeze the current shape.

### D11. crates.io builds and raster math

A `cargo install` from crates.io computes raster output with the platform libm, because
`[patch.crates-io]` only applies in this workspace. This contradicts "every build computes with
the same math library".

- **Recommended:** document the exception for 1.0 (#509), and fix it in 1.x by publishing
  the patched resvg-stack crates under project names, or by upstreaming the `libm` routing.
- Alternative: fix it before 1.0.

### D12. Licence metadata

Every crate declares `license = "EPL-2.0"`. But `graphviz-pure-core` ships an MIT port of
CORE-MATH, `graphviz-pure-geom` an MIT port of expat, and `graphviz-pure-raster` OFL fonts. The
wheel, Wasmer, conda and AUR metadata already say `EPL-2.0 AND OFL-1.1 AND MIT`, while npm and JSR
say `EPL-2.0`.

- **Recommended:** per-crate SPDX expressions (`EPL-2.0 AND MIT` for core and geom,
  `EPL-2.0 AND OFL-1.1` for raster), and the matching expression for npm/JSR. This needs the
  maintainer's (or counsel's) sign-off.

### D13. The `-V` line

`graphviz-pure -V` prints `graphviz-pure - graphviz-pure version 0.2.2 (Rust port…)`. C prints
`dot - graphviz version 16.1.0 (…)`, which the Python wrappers parse (docs/python.md lists
changing it as a next step).

- **Recommended:** decide before 1.0. After 1.0, changing the line is arguably breaking for
  anything that parses it. Match C's shape (for example `graphviz-pure - graphviz version
  16.1.0 (graphviz-pure 1.0.0)`) so `graphviz.version()` works.

### D14. Diagnostics from the library

Warnings and errors are written to stderr through thread-local state (`core::diag`), as C's
`agerr` does, even when the library is embedded.

- **Recommended:** not a 1.0 blocker. Returning diagnostics can be added post-1.0 as a new
  function. Under D1 (b), the current globals are internal.

## How this was measured

All of it ran on Linux x86-64, with Rust 1.99.1 and clippy 0.1.99:

- `cargo build --release -p graphviz-pure-diff -p graphviz-pure-cli -p graphviz-pure-portable-libm`.
- **Fidelity:** `target/release/gv-diff e2e --list`, the eight layout ratchets as in
  `scripts/update-baselines.sh` (without `--update`), and `gv-diff render`.
- **Skipped inputs:** C, run with `GVBINDIR=/opt/graphviz-16.1.0/lutplugins
  scripts/dot-portable-libm.sh`, four times per skipped input; then the whole corpus with
  `GV_PORTABLE_LIBM=<portable-libm built --features apple-libc> gv-diff e2e --generate --runs 2
  --c-dot scripts/dot-portable-libm.sh`.
- **Panic sites:** `scripts/panic-sites.sh`.
- **API:** item counts from `RUSTC_BOOTSTRAP=1 cargo rustdoc -p <crate> --lib -- -Z
  unstable-options --output-format json`; `cargo semver-checks -p graphviz-pure
  --baseline-version 0.2.1` (cargo-semver-checks 0.51.0, installed outside the repository):
  202 pass, 58 skip.
- **MSRV:** `grep -rln '&& let ' crates/*/src` (33 files), and `cargo metadata --locked`
  for `jpeg-encoder` 0.7.1 (`rust_version` 1.87).
- **Dangling references:** every `#NNN` in tracked text and source files, outside
  `tests/golden/` and `vendor/`, checked against the full list of issues and pull requests
  from the GitHub GraphQL API.
- **Channels:** `gh release view v0.2.2`, and the crates.io, npm, JSR, PyPI and Wasmer APIs
  (read only).
- **Formats:** `graphviz-pure -Tfoo` and `dot -Tfoo` (C, full plugin directory).
