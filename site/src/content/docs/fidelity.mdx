The port is checked against C Graphviz 16.1.0 in four ways, from the strictest to the broadest. All the corpus checks run in `cargo test --workspace` as ratchets: each has a committed baseline listing the files that match, and a file that stops matching fails the build. The numbers on this page are read from those runs and baselines by `scripts/site-data.py`; none are typed in by hand, except where marked.

Every build of the port computes with the same math library, compiled into it, on every platform: Linux, Windows, macOS and WASM write the same bytes, and the numbers below hold for all of them. The C reference computes with those same math functions: `scripts/dot-portable-libm.sh` loads them into the unmodified C `dot` in place of the system libm, so a difference is a difference in the port, never in the math library ([the math library](../porting/libm/)). The comparison with stock C on macOS, which calls Apple's libm, is [reported too](#stock-c-on-macos), for information.

## Full pipeline

`gv-diff e2e` runs the whole port, parse to layout to render, on every input of nine corpora and compares its `-Tsvg` output with C's. **Identical means equal bytes**, after dropping the one line that starts with `<!-- Generated by `, which names the program and its version. Nothing else is normalised.

Only hashes of C's output are committed (`tests/golden/e2e.libm-matched.json`, 64-bit FNV-1a of the normalised SVG), so the check runs without C installed. Each C reference was produced several times; inputs whose C output differed between runs, or that C crashed on, are recorded as unstable and skipped.

### Stock C on macOS

For information, never as a check: `gv-diff e2e --stock` compares the same output with stock C on macOS (`tests/golden/e2e.json`), which computes with Apple's libm. The port matches it on {fmt(stock.identical)} of {fmt(stock.total)} files. Of the {fmt(stock.differs.length)} that differ, {fmt(stock.libm_only)} differ only through Apple's libm: on each of them the port equals C computing with the same math. These are not bugs, by policy: the port never follows a platform libm, so that every machine gets the same picture.

<DiffList stock />

C itself is less consistent across platforms than that. In the historical cross-platform comparison, C built on Linux the way Homebrew builds it on macOS used glibc's math, `qsort` and `rand`, and matched C on macOS on {fmt(cLinux.agree)} of {fmt(cLinux.total)} files. The details are in [The math library](../porting/libm/).

## Layout

`gv-diff` (without `e2e`) compares geometry rather than bytes: it lays out each input with the port, reads C's `-Tdot` output for the same input, and checks the bounding box, every node's centre and size, every edge's spline, arrow endpoints and label positions, and every cluster box. A file is **exact** when every element is within tolerance: 1 pt for node positions, sizes and bounding boxes, 2 pt for edge splines (sampled Hausdorff distance) and labels. This is looser than byte identity, and it covers the per-engine corpora with C goldens kept as `.dot` files (`tests/golden/<engine>/`).

<LayoutTable />

The {twopi.total - twopi.exact} twopi files are a floating-point tie in edge routing that C itself breaks differently from run to run, so no fixed reference can match every C. The full-pipeline check skips the same inputs as unstable.

## Renderers

`gv-diff render` takes C's own layouts (`tests/golden/render/laid/*.dot`) and renders them with the port in no-layout mode (`-Kneato -n2`), next to C's renderings of the same layouts. Any difference comes from the output code (or node sizing, which `-n2` recomputes). Identity is byte for byte, generator comment aside.

<RenderTable />

The skipped `-Tplain` and `-Tplain-ext` references are ones C does not reproduce from run to run: for some converted labels C prints a string after `lib/common/output.c` has freed it, so the field holds whatever is left in that memory. Every stable reference matches, including `svg_inline` and `cmapx`; the format list and counts above come from the current render ratchet.

## C test graphs

`scripts/dot-broad-validate.sh` lays out every graph in the Graphviz 16.1.0 source tree (`graphs/`, `tests/graphs/`, `tests/regression_tests/`) with C and with the port, in five variants, and `gv-diff pairs` compares the layouts as above.

## Fuzzing

The corpora only contain inputs someone thought of. `scripts/fuzz-gen.py` generates random graphs from a seed (engine, size, topology, clusters, rank sets, attributes from the whole Graphviz table, and about 8% malformed input), and `scripts/fuzz-run.py` runs C and the port on each and compares stdout (generator comment aside) and exit status. Every difference was minimised and fixed against the C source, round by round; one reproducer per bug went into the corpus.

Identity is the share of comparable cases whose output and exit status both match C. Cases where C's output changes between two runs, C times out, or C crashes are excluded.

## The reference

C Graphviz 16.1.0, run with `GVBINDIR` pointing at a plugin directory that holds only its core, dot and neato plugins, and with the port's math functions in place of the system libm (`scripts/dot-portable-libm.sh`: `DYLD_INSERT_LIBRARIES` on macOS, `LD_PRELOAD` on Linux). With no Pango text-layout plugin available, C measures text with its built-in font metric tables, as the port does. A default installation, which measures text with Pango and cairo, will not match. [Set it up yourself](../verify/#the-c-reference).
